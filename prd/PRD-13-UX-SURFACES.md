## 1. Purpose and orientation

This PRD defines every user-facing surface of the Polkagent platform: what each
surface shows, how users interact with it, and how surfaces remain consistent
with each other and with the authoritative kernel state underneath.

Polkagent is a Rust-first, Polkadot-native agent platform with three equal
pillars: **Build** (create Polkadot products), **Act** (perform on-chain actions
and payments), and **Reach** (deliver the experience through the best available
surface). The UX must serve all three without privileging one pillar's workflow
over another.

### 1.1 Who should read this document

- **Product designers** implementing surfaces or writing specifications.
- **Front-end and CLI engineers** building presentation layers.
- **Kernel engineers** who need to understand what projections and events
  surfaces consume.
- **Operators** who need to know what fleet, audit, and monitoring surfaces
  will exist.
- **First-time readers** who want to understand how a Polkagent user
  experiences the platform.

### 1.2 What this document does not cover

- Internal kernel state machines (see PRD-03).
- Wire schemas and API contracts (see PRD-14).
- Security threat models (see PRD-15).
- PCA transport-level protocol details (see PRD-06).
- Marketplace registry internals (see PRD-12).

This PRD specifies *what users see and do*. Other PRDs specify *how the system
implements it*.

### 1.3 Key terms

| Term | Meaning in this PRD |
|---|---|
| **Surface** | A user-facing presentation of Polkagent state and controls: CLI, web, mobile, chat, or operator console. |
| **Projection** | A versioned read model derived from kernel events that surfaces render. Surfaces never write kernel state directly. |
| **Action card** | A structured, canonical rendering of a proposed effect or chain action. It is derived from typed data, not model prose. |
| **Agent Inbox** | The cross-surface view of pending approvals, active runs, receipts, and recovery actions. |
| **Agent Studio** | The web-based environment for creating, testing, configuring, evaluating, publishing, and deploying agents and products. |
| **Run timeline** | A durable, truthful view of a run's lifecycle: received, queued, working, waiting, approval, outcome. |
| **Progressive disclosure** | A UX principle: show the minimum needed for a task by default; reveal advanced details on demand. |
| **Canonical data** | Facts derived from typed kernel records, chain metadata, or verifiable evidence. |
| **Model narrative** | Text generated by an AI model. It is explanatory, never authoritative. |

## 2. UX principles

These principles govern every surface. They are not aspirational goals; they are
testable requirements with acceptance criteria.

### 2.1 Progressive disclosure

**Principle:** Simple tasks must be easy. Advanced inspection must be available.

- A DOT holder checking a balance sees a single number and its source.
- The same view allows expanding to show the chain profile, block height,
  account type, existential deposit, and proxy/multisig relationships.
- A developer scaffolding a project sees a guided wizard. An expert can edit
  the underlying `AgentSpec` YAML directly.
- An operator monitoring a fleet sees a status dashboard. Drilling down reveals
  individual run timelines, effect records, and audit evidence.

**Requirement UX-DISC-01:** Every surface must have a default "simple" view and
an "advanced" view. The simple view must be sufficient for the primary persona's
most common task. The advanced view must not require a different surface.

**Requirement UX-DISC-02:** Configuration through UI, CLI, and declarative files
must produce identical semantic results. No surface may expose a capability that
another surface cannot represent.

### 2.2 Canonical state versus model narrative separation

**Principle:** Model-generated text explains; kernel-derived data decides.

- Every action card, status display, receipt, and error message has a
  **canonical section** rendered from typed projection data and a visually
  distinct **narrative section** rendered from model output.
- The canonical section uses fixed, structured layouts. The narrative section
  uses prose with a clear visual boundary (different background, labeled
  header, distinct typography).
- A user must never need to read model narrative to understand what an action
  will do, what state a run is in, or what an error means.

**Research confirmation [V]:** This separation is non-negotiable. The action
card must show chain-derived facts — specifically `DryRunApi` execution results
and metadata-decoded calldata — as its authoritative content. The model's prose
is clearly secondary and is never the source of truth for what the user will
sign. The Gray Swan indirect-prompt-injection benchmark (reported in the Claude
Opus 4.5 system card, November 2025) demonstrates that any design relying on
model narrative as an authoritative source is vulnerable: even the most
injection-resistant frontier model fails under repeated adversarial attempts.
The only defensible posture is calldata-derived canonical cards with the model
in an explanatory-only role.

**Requirement UX-SEP-01:** Canonical and narrative sections must be visually
distinguishable in every surface, including CLI output, web cards, mobile views,
and chat messages.

**Requirement UX-SEP-02:** The canonical section must render correctly even when
the model narrative is empty, truncated, or loading. The narrative section must
never override, contradict, or replace canonical data fields.

**Requirement UX-SEP-03:** Automated tests must verify that a forged or
adversarial model narrative cannot alter the canonical section's content, layout,
or interactive controls in any surface.

### 2.3 Structured action cards for irreversible effects

**Principle:** Before a user approves an irreversible action, they see a
structured card derived from canonical data, not a model-generated summary.

- The card shows exactly what will happen: action verb, target chain/network,
  source and destination accounts, asset and amount, fees, risk indicators,
  and policy basis.
- The model may explain *why* the action is proposed, but that explanation is
  visually subordinate and clearly labeled as model-generated.
- The card's approve/deny controls are bound to the exact canonical payload.
  Approving a card approves its payload hash, not a model's description.

**Requirement UX-CARD-01:** Every effect with `EffectClass::Irreversible` or
`EffectClass::ValueMoving` must render as a structured action card before
approval.

**Requirement UX-CARD-02:** The card must render identically (in semantic
content) across all surfaces. Mobile and chat surfaces may use a compact
layout but must not omit required fields.

### 2.4 Truthful status

**Principle:** Never mask unknown as success or failure.

- The platform distinguishes: `pending`, `queued`, `working`, `waiting_input`,
  `waiting_approval`, `approved`, `denied`, `signed`, `submitted`, `included`,
  `finalized`, `failed`, `reverted`, `expired`, `cancelled`, and `unknown`.
- When the system does not know the outcome (network partition, timeout,
  signer unavailable), it says `unknown` and offers recovery actions.
- A "thinking" or "processing" animation must not replace a truthful status
  indicator. Animations may run alongside status, never instead of it.

**Requirement UX-TRUTH-01:** Every run, effect, and chain action must display
its current lifecycle state using the canonical state vocabulary. No state may
be hidden, combined with another state, or displayed as a different state.

**Requirement UX-TRUTH-02:** The `unknown` state must be visually distinct from
both `failed` and `succeeded`. It must include a timestamp, a description of
what is unknown, and at least one suggested recovery action.

### 2.5 Accessible by default

**Principle:** All surfaces must be usable by people with disabilities.

**Requirement UX-A11Y-01:** Web and PWA surfaces must conform to WCAG 2.1 AA.

**Requirement UX-A11Y-02:** All interactive elements must be keyboard-navigable
with visible focus indicators.

**Requirement UX-A11Y-03:** All images, icons, and status indicators must have
text alternatives. Color must not be the sole means of conveying information.

**Requirement UX-A11Y-04:** Screen readers must be able to navigate action
cards, run timelines, and approval flows without loss of semantic meaning.

**Requirement UX-A11Y-05:** CLI output must support `--no-color` and
`--plain-text` modes for assistive technology compatibility.

## 3. Persona journey maps

The following journeys illustrate how key personas interact with Polkagent
surfaces. Each journey names the persona, their goal, the surface(s) involved,
and the states they traverse.

- Balance reads require no approval and render immediately.

- If finality is unknown (e.g., network timeout), the status says `unknown`,
  not `failed`.

### 3.2 Developer: scaffold, test, deploy a project

**Persona:** Rust developer building a Polkadot SDK runtime. Uses CLI and
Studio. Wants to move from "new project" to "deployed on testnet" with agent
assistance.

**Entry surfaces:** CLI (primary), Studio (secondary).

#### Journey steps

```
1. SCAFFOLD
   $ polkagent new --template parachain --name my-chain
   Agent creates workspace, downloads template, initializes git.
   CLI shows progress as a run timeline:

     [✓] Applied template: parachain-template v1.15.0
     [✓] Initialized git repository
     [✓] Generated initial chain spec
     [ ] Ready. Run `polkagent build` to compile.
   ──────────────────────────────────────────────────────────────

2. EDIT WITH AGENT ASSISTANCE
   $ polkagent run "Add a pallet that stores a configurable u32 value"
   Agent uses coding harness (Claude Code, Codex, etc.).
   CLI shows streaming progress:
     Working... [pallet-value] Creating pallet skeleton
     Working... [pallet-value] Adding storage item
     Working... [pallet-value] Adding extrinsic set_value
     Working... [pallet-value] Updating runtime configuration
     Working... [pallet-value] Adding unit tests
   ──────────────────────────────────────────────────────────────

3. BUILD AND TEST
   $ polkagent build --test
   Agent runs cargo build and cargo test.
   CLI shows structured output:

5. DEPLOY TO TESTNET (requires approval)
   $ polkagent deploy --target paseo
   Action card appears in CLI:
     ┌──────────────────────────────────────────────────┐
     │ DEPLOY RUNTIME                       Risk: Medium│
     │ Target: Paseo testnet                            │
     │ Artifact: my-chain-runtime.wasm (sha256: a3f2...)│
```

#### Key UX requirements from this journey

- CLI provides structured, non-interactive output by default.
- Approval prompts in CLI use simple `[y/N]` for terminals.
- The same run is visible in both CLI and Studio; state is consistent.
- Build and test output is machine-parseable (`--format json` available).
- Network start/stop is explicit; no orphaned processes.

## 4. CLI surface

The CLI is the primary surface for developers and automation. It must be fast,
scriptable, and consistent with the kernel's domain vocabulary.

**Research finding [I]:** The Rust CLI must be built with `clap` (subcommand
architecture, derive macros). This is both an implementation requirement and a
user-facing quality requirement: `clap` provides the shell-completion
infrastructure (§4.4), consistent help output, and typed argument parsing that
produces reliable `--json` / `--format` output (§4.3). The first-run wizard
(§11.1), daemon interaction (§4.6), and conventional exit codes (§4.3) are all
validated by this research as must-have, not nice-to-have, for automation and
scripting use cases.

### 4.1 Command structure

### 4.2 Interactive and non-interactive modes

**Requirement UX-CLI-01:** The CLI must detect whether it is running in an
interactive terminal (TTY) or a pipe/script.

| Behavior | Interactive (TTY) | Non-interactive (pipe/CI) |
|---|---|---|
| Approval prompts | `[y/N]` prompt with timeout | Exit with code 2 and message |
| Progress display | Animated spinners and bars | Line-by-line status updates |
| Color output | ANSI colors (unless `--no-color`) | Plain text |
| Streaming model output | Character-by-character | Buffered paragraphs |
| Error display | Formatted with context | Single-line JSON or plain text |

**Requirement UX-CLI-02:** `--yes` flag skips approval prompts for actions the
user's current policy allows. It does not bypass policy; it uses a configured
autonomous mandate or session approval.

**Requirement UX-CLI-03:** `--dry-run` flag shows what would happen without
executing effects. It renders the action card and policy decision.

### 4.3 Output formatting

**Requirement UX-CLI-04:** All commands that produce structured output must
support `--format <format>` with at least:

| Format | Description |
|---|---|
| `human` | Default. Aligned, colored, readable text. |
| `json` | Machine-readable JSON. One object per line for streaming. |
| `json-pretty` | Indented JSON for human inspection. |
| `table` | Aligned columns with headers. |
| `csv` | Comma-separated values for spreadsheet import. |
| `yaml` | YAML for configuration compatibility. |

**Requirement UX-CLI-05:** JSON output must include a `_meta` field with the
command, version, timestamp, and any pagination tokens.

**Requirement UX-CLI-06:** Exit codes follow a consistent scheme:

| Code | Meaning |
|---|---|
| 0 | Success |
| 1 | General error |
| 2 | Approval required (non-interactive mode) |
| 3 | Policy denied |
| 4 | Configuration error |
| 5 | Network/chain error |
| 10 | Unknown outcome (effect submitted but finality not confirmed) |

### 4.4 Shell completions

**Requirement UX-CLI-07:** `polkagent completion <shell>` generates completions
for `bash`, `zsh`, `fish`, and `powershell`.

**Requirement UX-CLI-08:** Completions include subcommands, flags, agent names,
skill names, chain profile names, and format options.

### 4.5 Configuration via CLI

**Requirement UX-CLI-09:** `polkagent config` reads and writes the same
configuration files used by all surfaces. Configuration sources are layered:

```
1. Built-in defaults
2. System config:  /etc/polkagent/config.yaml
3. User config:    ~/.config/polkagent/config.yaml
4. Workspace:      .polkagent/config.yaml
5. Environment:    POLKAGENT_* variables
6. CLI flags:      --flag=value
```

Later sources override earlier ones. `polkagent config show --effective` shows
the merged result with source annotations.

### 4.6 CLI daemon interaction

**Requirement UX-CLI-10:** Commands that need a running daemon (`agent start`,
`inbox list`, `run`) connect to the local daemon via a Unix socket or TCP
port. If the daemon is not running, the CLI offers to start it.

**Requirement UX-CLI-11:** `polkagent doctor` checks:
- Rust toolchain version and components
- Daemon status and connectivity
- Chain profile validity and metadata freshness
- Signer availability
- Disk space and database integrity
- Network connectivity to configured RPC endpoints

## 6. Agent Inbox (F1)

The Agent Inbox is the unified cross-surface view of everything that needs
the user's attention. It exists in CLI, Studio, mobile, and chat surfaces.

**Research finding [I]:** The Inbox must function as a true notification center,
not just an approval queue. Research into comparable agent platforms identifies
three components that must appear together: (1) a notification center for
approval requests and alerts, (2) a real-time run timeline with streaming
progress (events appended as the run executes, not after it completes), and
(3) a fleet-level overview for multi-agent deployments. The run timeline's
streaming behavior requires ARIA live regions so that assistive technologies
announce new events without requiring a page reload (see §14).

### 6.1 Inbox categories

| Category | Contents | Priority |
|---|---|---|
| **Pending approvals** | Action cards awaiting human approval. Each has a deadline. | Highest |
| **Active runs** | Runs currently executing with live status. | High |
| **Alerts** | Circuit breakers, unknown outcomes, policy violations. | High |
| **Notifications** | Completed runs, receipts, system messages. | Normal |
| **History** | Past items, searchable and filterable. | Low |

### 6.2 Inbox items

Each inbox item has:

- **ID:** Stable, cross-surface identifier.
- **Type:** approval, run_status, alert, notification, receipt.
- **Agent:** Which agent created this item.
- **Summary:** One-line canonical description.
- **Created:** Timestamp.
- **Deadline:** For approvals, when the action expires.
- **Priority:** Derived from type and urgency.
- **Actions:** Available actions (approve, deny, view, dismiss, retry).

### 6.3 Pending approvals

A pending approval item shows the full action card (as defined in section 7)
plus:

- Time remaining before the action expires.
- Policy context: why approval is required (which policy rule triggered it).
- Quick approve/deny controls.
- "View details" link to the full run timeline.

**Requirement UX-INBOX-01:** Pending approvals must be sorted by deadline
(earliest first). Expired approvals must be visually marked and moved to
history.

**Requirement UX-INBOX-02:** Approving or denying in any surface must
immediately update all other surfaces. A user must not be able to approve
the same action twice.

### 6.4 Active runs status

Active runs show:

- Current state (working, waiting, approval).
- Duration so far.
- Latest event summary.
- Quick actions: view timeline, cancel, pause (if supported).

**Requirement UX-INBOX-03:** Active run status must update within 5 seconds of
a state change in the kernel.

### 6.5 Receipts and history

Completed items show:

- Outcome (success, failure, cancelled, unknown).
- Receipt details for chain actions (see section 3.1 for receipt format).
- Cost summary.
- Link to full run timeline.

**Requirement UX-INBOX-04:** History must support text search, date range
filtering, agent filtering, and outcome filtering. Results must be paginated.

### 6.6 Recovery actions

When an item has an `unknown` outcome or a recoverable error, the inbox must
show:

- What is unknown and why.
- Available recovery actions (retry, check status, cancel, escalate).
- The last known good state.

**Requirement UX-INBOX-05:** Recovery actions must be structured action cards
themselves. A retry of a chain action must render a new action card with
updated evidence (fresh nonce, current fees).

### 6.7 Cross-surface consistency

**Requirement UX-INBOX-06:** The Inbox must show the same items with the same
states regardless of which surface renders it. Inbox state is a kernel
projection, not surface-local state.

**Requirement UX-INBOX-07:** An action taken in one surface (approve in CLI)
must be reflected in all other surfaces (Studio, mobile, chat) within 5
seconds.

## 7. Structured action card (F2)

The structured action card is the most safety-critical UX element in
Polkagent. It is the interface between the system's intent and the user's
decision.

### 7.1 Anatomy of an action card

Every action card has the following structure:

```
┌─────────────────────────────────────────────────────────────┐
│ HEADER                                                      │
│  Action verb + type          Risk indicator (Low/Med/High)  │
├─────────────────────────────────────────────────────────────┤
│ CANONICAL DATA SECTION                                      │
│  Structured fields derived from typed kernel data.          │
│  Never from model output.                                   │
│                                                             │
│  Field layout depends on action family:                     │
│  - Transfer: from, to, amount, asset, fee, network         │
│  - Vote: referendum, track, conviction, account             │
│  - Deploy: artifact, target, action, account                │
│  - Contract call: contract, method, args, value, gas        │
│  - ...                                                      │
│                                                             │
│  Always includes:                                           │
│  - Source account and signing method                        │
│  - Target network and chain profile evidence                │
│  - Estimated or exact fee                                   │
│  - Validity period                                          │
│  - Policy basis (which grant/mandate allows this)           │
├─────────────────────────────────────────────────────────────┤
│ PREFLIGHT EVIDENCE (expandable)                             │
│  Simulation results, balance checks, ED checks,            │
│  proxy filter verification, nonce, metadata hash.           │
│  Marked as available or unavailable per field.              │
├─────────────────────────────────────────────────────────────┤
│ MODEL EXPLANATION (visually distinct)                       │
│  ┌─ AI-generated explanation ─────────────────────────────┐ │
│  │ "This vote supports referendum 542, which proposes..." │ │
│  │ This text is generated by the AI model. It does not    │ │
│  │ determine what the action does — the canonical data    │ │
│  │ above is authoritative.                                │ │
│  └────────────────────────────────────────────────────────┘ │
├─────────────────────────────────────────────────────────────┤
│ RISK INDICATORS (if any)                                    │
│  ⚠ First interaction with this address                      │
│  ⚠ Amount exceeds your daily transfer history               │
│  ⚠ Batch contains 3 inner calls (expand to review)         │
├─────────────────────────────────────────────────────────────┤
│ CONTROLS                                                    │
│  [ Approve ]    [ Deny ]    [ Edit ]    [ Details ]        │
│                                                             │
│  Approving binds to payload hash: 0x7f3a...                │
│  Expires in: 4m 32s                                         │
└─────────────────────────────────────────────────────────────┘
```

### 7.2 Canonical data fields

The following fields are rendered from typed kernel data. They must never be
populated from model output.

| Field | Source | Required |
|---|---|---|
| Action type/verb | `EffectIntent.effect_type` | Always |
| Source account | `ChainIntent.from_account` | Always |
| Target network | `ChainProfile.network_name` | Always |
| Chain profile evidence | `ChainProfile.genesis_hash`, `spec_version`, `metadata_hash` | Always |
| Estimated fee | Preflight evidence or `unknown` | Always |
| Validity period | `ChainIntent.mortality` | When applicable |
| Policy basis | `PolicyDecision.grant_ref` | Always |
| Recipient/destination | `ChainIntent.destination` | When applicable |
| Asset and amount | `ChainIntent.asset`, `ChainIntent.amount` | When applicable |
| Call data (decoded) | Metadata-decoded extrinsic fields | Always (expandable) |
| Simulation/dry-run | `PreflightEvidence` fields | When available |
| Nonce | `ChainIntent.nonce` | Always |
| Payload hash | Hash of the exact signing payload | Always |

### 7.3 Model explanation area

The model explanation area is:

- Visually separated from canonical data (different background color,
  indented, with a header label).
- Clearly labeled: "AI-generated explanation" or equivalent.
- Optional: the card must render correctly without it.
- Truncated with "show more" if it exceeds 3 lines in compact view.

**Requirement UX-CARD-03:** A model explanation must not contain interactive
elements (buttons, links that trigger actions). It is read-only text.

**Requirement UX-CARD-04:** If the model explanation contradicts canonical data
(e.g., says "sending 10 DOT" when the canonical amount is 5 DOT), the card
must display a warning: "Model explanation may not match the canonical action
data. Always verify using the canonical fields above."

### 7.4 Approval/deny controls

- **Approve:** Binds approval to the exact payload hash. Shows the hash.
  Triggers signer flow if applicable.
- **Deny:** Records denial with optional reason. Terminates the action.
- **Edit:** Returns to the agent with modification instructions. Creates a
  new intent (new payload, new card).
- **Details:** Expands all sections, shows raw data, links to run timeline.

**Requirement UX-CARD-05:** The [Approve] button must display the payload hash
it will bind to. If the payload changes between card render and approval, the
card must refresh and re-present.

**Requirement UX-CARD-06:** Approval must require a deliberate action (click,
tap, or explicit CLI confirmation). It must not be triggerable by keyboard
shortcut alone, timer, or auto-approve without a configured mandate.

### 7.5 Risk indicators

Risk indicators are derived from canonical data and policy rules, not from
model assessment.

| Indicator | Trigger | Severity |
|---|---|---|
| First address | Recipient not in user's known-address set | Medium |
| High amount | Amount exceeds configurable threshold | Medium |
| Batch/nested calls | Call contains inner calls | Medium |
| Proxy operation | Action modifies proxy/delegation relationships | High |
| Cross-chain | XCM destination differs from source | Medium |
| Unknown simulation | Dry-run unavailable or incomplete | Medium |
| Stale metadata | Profile metadata older than configurable threshold | High |
| Near ED | Result would bring account near existential deposit | Medium |
| Unknown fee | Fee estimation unavailable | Medium |

**Requirement UX-CARD-07:** Risk indicators must be testable. Each indicator
must have a fixture that triggers it and a fixture that does not.

### 7.6 "What will change" simulation panel

**Research finding [I]:** The action card's preflight evidence section must
present a simulation-derived change summary modeled on the patterns established
by MetaMask, Phantom, and the AP2 payment-mandate chain (Intent → Cart →
Payment Mandate as W3C Verifiable Credentials). Users in those ecosystems have
developed an expectation for explicit pre-sign state-change disclosure; Polkagent
must meet or exceed that standard.

The simulation panel renders inside the PREFLIGHT EVIDENCE section (see §7.1)
when `DryRunApi` and `XcmPaymentApi` results are available. It shows:

```
┌─────────────────────────────────────────────────────────┐
│ WHAT WILL CHANGE (chain-simulated)                      │
├─────────────────────────────────────────────────────────┤
│ Your free balance:  142.85 DOT  →  137.83 DOT  (−5.02) │
│ Fee:                ~0.0152 DOT (estimated from chain)  │
│ Destination:        5HGj...Yz4k (first interaction ⚠)  │
│ Recipient balance:  12.50 DOT   →  17.50 DOT  (+5.00)  │
│ ED check:           PASS (both accounts above 1 DOT ED) │
│ Risk indicator:     Low                                 │
├─────────────────────────────────────────────────────────┤
│ Simulated using DryRunApi · block #23,456,789            │
└─────────────────────────────────────────────────────────┘
```

When simulation is not available, the panel must show an explicit state rather
than omitting the section entirely:

```
┌─────────────────────────────────────────────────────────┐
│ SIMULATION PENDING                                      │
│ DryRunApi result not yet available. Do not approve      │
│ until simulation completes or you have independently    │
│ verified the effect.                   [ Retry ]        │
└─────────────────────────────────────────────────────────┘
```

**Requirement UX-CARD-09:** When `DryRunApi` results are available, the action
card must show balance deltas, actual fee, destination, and a risk indicator
derived from chain-computed data — never from model estimate alone.

**Requirement UX-CARD-10:** Unknown or pending simulation state must be
explicitly labeled. The card must never omit the simulation panel silently or
present a blank section that could be mistaken for a completed simulation.

**Requirement UX-CARD-11:** Simulation results must include their evidence
source: the API used, block height at query time, and whether the result is
exact or estimated.

### 7.7 High-stakes confirmation patterns

For actions with risk indicator `High` (proxy operations, large amounts, first
address, stale metadata), the approval interaction adds deliberate friction to
ensure the user has considered the action.

**Desktop/web:** The [Approve] button requires a two-step confirmation: first
click changes the button label to "Confirm approval — binding to 0x7f3a…";
second click within 5 seconds completes the approval. Outside that window, the
button resets. A hold-to-approve pattern (press and hold for 2 seconds) is
an acceptable alternative for High-risk actions.

**Mobile/touch:** Swipe-to-confirm replaces the tap button for High-risk
actions. The user swipes a slider from left to right; releasing before the
threshold cancels. This prevents accidental approval from a stray tap.

**CLI:** For High-risk actions in interactive mode, the CLI prompts for
explicit typed confirmation rather than `[y/N]`:

```
  ⚠ HIGH RISK ACTION: proxy operation
  Type "confirm proxy change" to approve, or press Enter to deny:
```

**Risk-tiered friction summary:**

| Risk level | Desktop | Mobile | CLI |
|---|---|---|---|
| Low | Single click | Tap | `[y/N]` prompt |
| Medium | Single click + payload hash shown | Tap + hash shown | `[y/N]` with hash |
| High | Two-step or hold-to-approve | Swipe-to-confirm | Typed confirmation |

**Requirement UX-CARD-12:** High-risk action cards must use an interaction
pattern that requires a distinct deliberate gesture beyond a single tap or click.

**Requirement UX-CARD-13:** The swipe-to-confirm and hold-to-approve controls
must be keyboard-accessible equivalents (e.g., hold Enter key for the hold
duration, or a two-step Tab+Enter flow) so they do not fail WCAG 2.1 AA
keyboard-navigation requirements.

### 7.8 Compact variants

For space-constrained surfaces (mobile, chat), the action card has a compact
variant that shows above the fold:

1. Action verb and type
2. Key value (e.g., amount and asset)
3. Counterparty (e.g., recipient address, abbreviated)
4. Fee
5. Risk flags (icons)
6. Approve/Deny buttons

"View full card" expands or navigates to the complete card.

**Requirement UX-CARD-08:** The compact card must include all information
necessary for a competent user to make an approval decision for a simple
transfer. Complex actions (batches, proxy changes, XCM) must always show
the full card.

## 8. Mobile and chat surface

### 8.1 Surface strategy

Polkagent's mobile strategy prioritizes reaching users where they already are,
while maintaining a robust fallback when experimental host APIs are unavailable.

**Priority order for mobile delivery:**

1. **PCA-compatible chat** in Polkadot App (preserve existing user behavior).
2. **Responsive web/PWA** accessible from any mobile browser.
3. **Polkadot App Product companion** (when host APIs stabilize).
4. **Alternative chat adapters** (Matrix, Telegram, Discord) as non-equivalent
   reach extensions.
5. **Dedicated native mobile app** (only if the above do not provide adequate
   UX).

**Requirement UX-MOBILE-01:** Polkagent must not depend on a single
experimental mobile API for its core experience. The responsive web/PWA must
provide a complete fallback for all non-chat functionality.

### 8.2 PCA-compatible chat interface

For users who interact through Polkadot App chat (the PCA transport),
Polkagent must:

- Render text responses within transport message limits.
- Provide compact action cards that fit within chat constraints.
- Support inline approval/deny (if the host supports interactive elements)
  or link to the web Inbox for approval.
- Handle file and media attachments via the HOP/Bulletin path.
- Maintain conversation context across sessions and devices.

**Requirement UX-MOBILE-02:** Chat messages must degrade gracefully. If the
transport does not support structured cards, render a text summary with a
link to the web Inbox for the full card.

**Requirement UX-MOBILE-03:** Chat must never be the only surface for
approving irreversible actions. A web or CLI approval path must always exist.

### 8.3 Responsive web/PWA

The responsive web surface is Studio optimized for mobile viewport:

- Simplified navigation (bottom tab bar).
- Touch-optimized controls (minimum 44px touch targets).
- Inbox-first layout (approvals and active runs are prominent).
- Reduced information density (single column, expandable sections).
- Offline support for reading cached state (service worker).
- Push notifications (Web Push API) for approvals and alerts.

**Requirement UX-MOBILE-04:** The PWA must score 90+ on Lighthouse
accessibility and performance audits.

**Requirement UX-MOBILE-05:** The PWA must be installable on iOS Safari and
Android Chrome with appropriate manifest and icons.

### 8.4 Polkadot App Product companion

If and when the Polkadot App host provides stable, tested APIs for:

- Bot/agent identity and presence
- Structured message types or interactive cards
- Host-mediated signing for agent-proposed payloads
- Push/background notification
- File/attachment delivery

...then a Product companion may be developed as a surface adapter.

### 10.3 Research-validated UX build staging

The following staging is derived from cross-domain research synthesis (Domain
13, research3.md) and overrides any conflicting priority ordering within this
document.

**do-now (Phase 0–1):**
- Calldata-derived action card (§7.1–§7.5) built on DryRunApi and
  metadata-decoded extrinsic data. This is the platform's safety signature and
  must be present before any value-moving capability ships.
- Run timeline (§5.2.2, §6) with real-time streaming updates.
- Rust CLI with `clap` (§4), including `--json` output, shell completions,
  first-run wizard, and conventional exit codes.

**validate-next (Phase 2):**
- "What will change" simulation UX (§7.6) — the full simulation panel with
  balance deltas, fee, destination, and risk indicator derived from DryRunApi.
  Needs DryRunApi integration working first.
- Audit log viewer (§9.3) — schema must be designed in Phase 0 even if the
  viewer ships in Phase 2.

**defer (Phase 3+):**
- Fleet dashboard (§9.1) — useful for multi-agent operators but not required
  before single-agent use cases are validated.
- Dedicated native mobile app (§8.1 item 5) — PWA is the mobile story until
  there is evidence the PWA cannot serve the use case.

**avoid (all phases):**
- Model-narrated confirmations: the model must never be the source of what the
  user is asked to approve. Model explanation is always secondary and clearly
  labeled.
- Hidden pending states: simulation pending, finality unknown, and signer
  unavailable must always be surfaced explicitly. Never substitute a loading
  spinner for a truthful state label.

## 12. Error and recovery UX (F7)

### 12.1 Error message pattern

Every error displayed to a user must follow this structure:

```
┌─────────────────────────────────────────────────────┐
│ ERROR: [Category] [Short description]               │
├─────────────────────────────────────────────────────┤
│ What happened:                                      │
│   [Plain-language description of the error]         │
│                                                     │
│ What is safe:                                       │
│   [What was NOT affected by this error]             │
│                                                     │
│ What you can do:                                    │
│   1. [First recovery option]                        │
│   2. [Second recovery option]                       │
│   3. [Escalation option]                            │
│                                                     │
│ Details:                                            │
│   Error ID: err_7f3a2b1c                            │
│   Time: 2026-07-30 14:23:45 UTC                     │
│   Run: run_abc123 (if applicable)                   │
│   Effect: effect_def456 (if applicable)             │
└─────────────────────────────────────────────────────┘
```

**Requirement UX-ERR-01:** Every error must include "What is safe" — the user
must know what was NOT affected. For example: "Your funds were not moved. The
transaction was not submitted."

**Requirement UX-ERR-02:** Every error must include at least one actionable
recovery option. "Contact support" alone is not sufficient unless all
automated recovery paths have been exhausted.

### 12.2 Error categories

| Category | Description | Example |
|---|---|---|
| `config` | Configuration problem | Missing API key, invalid chain profile |
| `network` | Network connectivity | RPC endpoint unreachable, timeout |
| `chain` | Chain/runtime error | Stale metadata, dispatch error, insufficient balance |
| `policy` | Policy denial | Action not permitted by current grants |
| `signer` | Signing error | Signer unavailable, user denied in wallet |
| `model` | Model/provider error | Rate limit, context too large, provider down |
| `system` | Internal system error | Database corruption, disk full |

### 12.3 Recovery action suggestions

| Error scenario | Recovery actions |
|---|---|
| Transaction dispatch error | Show decoded error, suggest fix, offer retry with new card |
| Unknown finality | Show last known state, offer to check status, offer manual resolution |
| Insufficient balance | Show required amount, current balance, and ED. Do not suggest deposits. |
| Stale metadata | Offer to refresh profile. Show what might change. |
| Provider rate limit | Show retry time. Offer to switch provider. |
| Signer timeout | Offer to retry signing. Show the pending action card. |
| Circuit breaker triggered | Show trigger cause. Offer to investigate, adjust threshold, or resume. |

### 12.4 Unknown state handling

When the outcome of an effect is unknown (the most dangerous state):

**Requirement UX-ERR-03:** The unknown state must:

1. Be visually distinct (yellow/amber warning, not red error or green success).
2. State exactly what is unknown: "The transaction was submitted but finality
   has not been confirmed."
3. State what might have happened: "The transaction may have succeeded,
   failed, or been dropped."
4. Provide a manual check path: "You can check the transaction status at
   [explorer link] using tx hash 0x9a3f..."
5. Provide a safe retry path: "If the transaction was not included, you can
   retry with a new action card (new nonce)."
6. Never automatically retry an unknown-state effect. The user must confirm.

**Requirement UX-ERR-04:** The `unknown` state must never automatically
transition to `failed` or `succeeded` without new evidence. If evidence
arrives later (e.g., block inclusion detected), the state updates and the
user is notified.

### 12.5 Support escalation

**Requirement UX-ERR-05:** When all automated recovery options are exhausted,
the error must offer:

1. Copy error details (for pasting into a support channel).
2. Export a diagnostic bundle (sanitized: no keys, no model content unless
   opted in).
3. Link to documentation for the error category.
4. Link to community support channels.

## 14. Accessibility

### 14.1 WCAG compliance

**Requirement UX-A11Y-01 (repeated):** Web and PWA surfaces must conform to
WCAG 2.1 Level AA. This includes but is not limited to:

- **Operable:** All functionality available from keyboard. No timing traps.
  Content does not cause seizures. Navigable.
- **Understandable:** Readable text. Predictable behavior. Input assistance.
- **Robust:** Compatible with assistive technologies.

### 14.2 Keyboard navigation

**Requirement UX-A11Y-06:** All surfaces must define a logical tab order:

- In Studio: sidebar navigation, then main content, then action buttons.
- In action cards: canonical data, then risk indicators, then controls
  (Approve, Deny, Edit, Details).
- In the Inbox: item list, then item detail, then item actions.

**Requirement UX-A11Y-07:** Keyboard shortcuts must be available for common
actions:

| Shortcut | Action | Surface |
|---|---|---|
| `?` | Show keyboard shortcuts | Web |
| `g i` | Go to Inbox | Web |
| `g d` | Go to Dashboard | Web |
| `g a` | Go to Agents | Web |
| `j` / `k` | Next / previous item in lists | Web |
| `Enter` | Open selected item | Web |
| `Escape` | Close modal / go back | Web |

### 14.3 Screen readers

**Requirement UX-A11Y-08:** Action cards must use ARIA landmarks and roles:

- Card container: `role="region"` with `aria-label="Action card: [type]"`
- Canonical section: `role="group"` with `aria-label="Canonical action data"`
- Model explanation: `role="note"` with `aria-label="AI-generated explanation"`
- Risk indicators: `role="alert"` for high severity, `role="status"` for medium
- Controls: standard button roles with descriptive labels

**Requirement UX-A11Y-09:** Run timeline events must be navigable as a list.
Each event must announce its type, time, and summary.

**Requirement UX-A11Y-12:** Streaming run timeline updates must use ARIA live
regions so that assistive technologies announce new events as they arrive.
Specifically:

- The run timeline container must use `aria-live="polite"` so that new events
  are announced without interrupting ongoing speech.
- Approval requests that arrive while a user is on another view must use
  `aria-live="assertive"` in the Inbox badge or notification area.
- Streaming model output (token-by-token) must not trigger individual live
  region announcements per token; instead, the region must use
  `aria-atomic="false"` and announce at paragraph or meaningful chunk
  boundaries.
- Simulation panel status changes (pending → available, or pending → failed)
  must be announced via a live region with a clear state description.

**Requirement UX-A11Y-13:** Full keyboard navigation must be available for all
approval and run-inspection flows, including the swipe-to-confirm and
hold-to-approve patterns defined in §7.7, which must have keyboard equivalents
that do not require a mouse or touch input.

### 14.4 Color and contrast

**Requirement UX-A11Y-10:** The platform must support light and dark themes.
Both themes must meet WCAG 2.1 AA contrast ratios (4.5:1 for normal text,

**Requirement UX-A11Y-11:** Status indicators must use both color and shape/icon:

#### A.1.2 Event Loop

The event loop follows Bardo's `app.rs` pattern: poll input, drain async
channels, tick animations, render, flush. Tokio drives background tasks; the
render path stays on the main thread with `crossbeam::channel` or
`std::sync::mpsc` for inter-thread communication.

```rust
pub fn run<B: Backend>(
    &mut self,
    terminal: &mut Terminal<B>,
) -> Result<()> {
    let mut last_frame = Instant::now();

    loop {
        let frame_start = Instant::now();
        let dt = frame_start.duration_since(last_frame).as_secs_f64();

        // 1. Poll input (non-blocking, ~0.1ms budget)
        let timeout = FRAME_DURATION.saturating_sub(last_frame.elapsed());
        if crossterm::event::poll(timeout)? {
            if let crossterm::event::Event::Key(key) = crossterm::event::read()? {
                self.last_input = Instant::now();
                if let Some(action) = self.handle_key(key) {
                    self.apply_action(action);
                }
            }
        }

        // 2. Drain async event channels (~0.5ms budget)
        self.drain_approval_channel();
        self.drain_agent_stream_chunks();
        self.drain_chain_subscription();
        self.poll_fs_watch();

        // 3. Tick animations (~1.0ms budget)
        self.tui_state.atmosphere.tick(dt);
        self.tui_state.channels.tick(dt as f32);
        self.tui_state.scroll_accel.tick(dt);

        // 4. Render — zero I/O, reads state only (~4ms budget)
        self.frame_counter = self.frame_counter.wrapping_add(1);
        if self.frame_counter % FLUSH_DIVISOR == 0 || self.tui_state.dirty {
            terminal.draw(|frame| self.render(frame))?;
            self.tui_state.dirty = false;
        }

        // 5. Exit check
        if !self.running {
            break;
        }

        last_frame = frame_start;
    }

    Ok(())
}
```

#### A.1.4 Render Pipeline

The render pipeline follows Roko's staged approach: layout computation,
view rendering, widget rendering, PostFX overlay, terminal flush.

```rust
fn render(&self, frame: &mut Frame) {
    let size = frame.area();
    let bp = LayoutBreakpoint::from_cols(size.width);

    // Stage 1: Compute layout regions
    let layout = PolkagentLayout::compute(size, bp);

    // Stage 2: Render chrome (header bar, status bar, tab bar)
    self.render_header_bar(frame, layout.header);
    self.render_tab_bar(frame, layout.tab_bar);
    self.render_status_bar(frame, layout.status_bar);

    // Stage 3: Render the active region's view
    match self.active_tab {
        Tab::Dashboard  => self.render_dashboard(frame, layout.main),
        Tab::Agents     => self.render_agents(frame, layout.main),
        Tab::Runs       => self.render_runs(frame, layout.main),
        Tab::Polkadot   => self.render_polkadot(frame, layout.main),
        Tab::Knowledge  => self.render_knowledge(frame, layout.main),
        Tab::System     => self.render_system(frame, layout.main),
    }

    // Stage 4: Render modal overlay (if any)
    if let Some(modal) = &self.modal {
        self.render_modal(frame, modal, size);
    }

    // Stage 5: Render notification toasts
    self.render_notifications(frame, size);

    // Stage 6: PostFX pass (bloom, atmosphere, scanlines)
    if self.tui_state.fx_config.enabled {
        self.render_postfx(frame, size);
    }
}
```

#### A.1.5 Frame Budget (at 60fps = 16.6ms total)

| Phase | Budget | Notes |
|---|---|---|
| Input polling | ~0.1ms | Non-blocking crossterm poll |
| Channel drain | ~0.5ms | Approval, stream, chain, fs channels |
| Animation tick | ~1.0ms | Atmosphere, interpolating channels, scroll accel |
| Layout compute | ~0.3ms | Rect arithmetic only |
| View render | ~2.5ms | Widget tree construction (ratatui immediate mode) |
| PostFX pass | ~1.0ms | Scanlines, bloom, atmosphere overlay |
| Terminal flush | ~2.0ms | Differential cell comparison + write |
| **Total** | **~7.4ms** | 44% of 16.6ms budget — comfortable headroom |

**Adaptive frame rate:** When no input has been received for 5 seconds, the
flush divisor increases from 6 to 12 (effectively ~5fps), reducing CPU load
during idle monitoring. Any input event resets to the full rate immediately.

#### A.1.6 Terminal Initialization and Teardown

```rust
pub fn enter_tui() -> Result<Terminal<CrosstermBackend<Stdout>>> {
    enable_raw_mode()?;
    let mut stdout = io::stdout();
    execute!(stdout, EnterAlternateScreen, EnableMouseCapture)?;
    let backend = CrosstermBackend::new(stdout);
    let mut terminal = Terminal::new(backend)?;
    terminal.clear()?;
    Ok(terminal)
}

pub fn exit_tui(terminal: &mut Terminal<CrosstermBackend<Stdout>>) -> Result<()> {
    disable_raw_mode()?;
    execute!(
        terminal.backend_mut(),
        LeaveAlternateScreen,
        DisableMouseCapture
    )?;
    terminal.show_cursor()?;
    Ok(())
}
```

Teardown is called in a `Drop` guard to ensure raw mode is always restored, even
on panic. Reference: Roko's `app.rs` uses `std::panic::catch_unwind` to
guarantee `disable_raw_mode()` runs.

## APPENDIX B: ROSEDUST DESIGN SYSTEM FOR POLKAGENT

### B.1 Color Palette

Polkagent adapts ROSEDUST from Roko and Bardo with Polkadot-specific extensions.
The rose family and semantic colors are preserved exactly; a DOT-pink extension
adds on-chain identity.

#### B.1.1 Background Hierarchy

| Token | Rust constant | RGB | Hex | Usage |
|---|---|---|---|---|
| `bg-void` | `BG_VOID` | (6, 6, 8) | `#060608` | Deepest background. The void. |
| `bg-raised` | `BG_RAISED` | (12, 10, 14) | `#0C0A0E` | Card and panel backgrounds. |
| `bg-mid` | `BG_MID` | (8, 8, 16) | `#080810` | Elevated surfaces with violet undertone. |
| `bg-warm` | `BG_WARM` | (10, 8, 8) | `#0A0808` | Warm-tinted backgrounds (agent activity). |
| `bg-highlight` | `BG_HIGHLIGHT` | (34, 28, 36) | `#221C24` | Selection highlight. |

Never use pure black (`#000000`). Every background has a faint chromatic tint
that prevents the visual flatness of pure black. This is the Roko/Bardo palette
precisely — confirmed by `apps/bardo-terminal/src/design/palette.rs` test
assertions.

#### B.1.2 Rose Palette (Primary Accent)

Rose is Polkagent's dominant accent. It signals activity, attention, and agent
state.

| Token | Rust constant | RGB | Hex | Usage |
|---|---|---|---|---|
| `rose-deep` | `ROSE_DEEP` | (58, 32, 48) | `#3A2030` | Deepest rose, for subtle backgrounds |
| `rose-ember` | `ROSE_EMBER` | (72, 40, 56) | `#482838` | Very dim rose, structural elements |
| `rose-dim` | `ROSE_DIM` | (122, 80, 96) | `#7A5060` | Muted, inactive, borders |
| `rose` | `ROSE` | (170, 112, 136) | `#AA7088` | Standard accent, active elements |
| `rose-bright` | `ROSE_BRIGHT` | (204, 144, 168) | `#CC90A8` | Active, highlighted, selection |

The OKLCH coordinates for the rose anchor: `OKLCH(0.65, 0.10, 12°)`. All rose
variants maintain equal hue (H ≈ 10–15°) with varying lightness L.

#### B.1.3 Semantic Colors

| Token | Rust constant | RGB | Hex | Meaning |
|---|---|---|---|---|
| `success` (jade) | `SUCCESS` | (112, 136, 122) | `#70887A` | Success, finalized, healthy |
| `warning` (amber) | `WARNING` | (170, 136, 85) | `#AA8855` | Warning, approaching threshold |
| `danger` (crimson) | `DANGER` | (204, 144, 168) | `#CC90A8` | Error, failed, denied |
| `dream` (violet) | `DREAM` | (88, 88, 120) | `#585878` | Knowledge, memory, info |
| `bone` | `BONE` | (200, 184, 144) | `#C8B890` | Highlight text, secondary accent |

#### B.1.4 Text Hierarchy

| Token | Rust constant | RGB | Hex | Usage |
|---|---|---|---|---|
| `text-phantom` | `TEXT_PHANTOM` | (32, 24, 32) | `#201820` | Invisible, structural only |
| `text-ghost` | `TEXT_GHOST` | (48, 40, 48) | `#302830` | Tertiary, decorative, timestamps |
| `text-dim` | `TEXT_DIM` | (88, 72, 88) | `#584858` | Secondary, supporting text |

| Token | Rust constant | RGB | Usage |
|---|---|---|---|
| `border` | `BORDER` | (24, 20, 32) | Unfocused panel border |

| `border-dream` | `BORDER_DREAM` | (88, 88, 120) | Knowledge panel border |

#### B.1.6 Polkadot-Specific Extensions

| Token | RGB | Hex | Usage |
|---|---|---|---|
| `dot-pink` | (230, 0, 122) | `#E6007A` | Polkadot brand color, used sparingly |
| `dot-pink-dim` | (115, 0, 61) | `#73003D` | Muted DOT pink for backgrounds |
| `parachain-violet` | (100, 80, 180) | `#6450B4` | Parachain / XCM indicators |
| `finalized-teal` | (80, 180, 160) | `#50B4A0` | Finality confirmed indicator |
| `pending-amber` | (200, 150, 60) | `#C8963C` | Pending/unconfirmed state |

The `dot-pink` is used only for:
1. The Polkadot logo glyph in the header bar
2. The `Chain: Polkadot` status indicator (small, not dominant)
3. The `⬡` extrinsic icon on action cards (relay chain only)

It must not override rose as the primary accent. Polkadot's brand pink is high
chroma and conflicts visually with rose; isolation to specific chain-identity
elements preserves the ROSEDUST aesthetic.

```rust
            dot_pink: reset, parachain_violet: reset,
            finalized_teal: reset, pending_amber: reset,
            scanline_dark: reset, phosphor_res: reset,
            noise_warm: reset, noise_cool: reset,
        }
    }

    /// Construct from environment variables.
    pub fn from_env() -> Self {
        if std::env::var_os("NO_COLOR").is_some() {
            Self::no_color()
        } else {
            Self::dark()
        }
    }

    // -- Style helpers --

    pub fn focused_border(&self) -> Style {
        Style::default().fg(self.border_active)
    }

    pub fn unfocused_border(&self) -> Style {
        Style::default().fg(self.border)
    }

    pub fn active_tab(&self) -> Style {
        Style::default()
            .fg(self.rose_bright)
            .add_modifier(Modifier::BOLD)
    }

    pub fn inactive_tab(&self) -> Style {
        Style::default().fg(self.text_dim)
    }

    pub fn status_active(&self) -> Style {
        Style::default().fg(self.success).add_modifier(Modifier::BOLD)
    }

    pub fn status_error(&self) -> Style {
        Style::default().fg(self.danger).add_modifier(Modifier::BOLD)
    }

    pub fn status_warning(&self) -> Style {
        Style::default().fg(self.warning).add_modifier(Modifier::BOLD)
    }

    pub fn status_unknown(&self) -> Style {
        Style::default().fg(self.warning)
    }

    /// Lifecycle state color (maps run/agent lifecycle to palette).
    pub fn lifecycle_color(&self, state: &str) -> Color {
        match state {
            "finalized" | "succeeded" | "active" => self.success,
            "working" | "signed" | "submitted" | "included" => self.rose,
            "waiting_approval" | "pending" | "queued" => self.warning,
            "unknown" => self.warning,
            "failed" | "reverted" | "denied" | "expired" => self.danger,
            "cancelled" | "stopped" | "idle" => self.text_dim,
            _ => self.text_primary,
        }
    }

    /// Progress bar color using semantic gradient (0.0=danger → 1.0=success).
    pub fn progress_color(&self, ratio: f64) -> Color {
        if ratio >= 0.75 { self.success }
        else if ratio >= 0.4 { self.warning }
        else { self.danger }
    }
}
```

#### B.2.1 Responsive Breakpoints

Adopted directly from Bardo's `apps/bardo-terminal/src/layout.rs`:

| Breakpoint | Width | Panels | Sidebar | Description |
|---|---|---|---|---|

#### B.3.2 Scanlines

Every other row is rendered with `SCANLINE_DARK` background, creating a subtle
CRT scanline pattern. The density (fraction of darkened rows) increases with
agent activity load.

```rust
fn apply_scanlines(frame: &mut Frame, area: Rect, intensity: f32, theme: &Theme) {
    for y in (area.y..area.y + area.height).step_by(2) {
        // Every even row gets a slightly darkened background cell
        // painted only over empty/whitespace cells to avoid overwriting content
        frame.render_widget(
            Block::default().style(Style::default().bg(theme.scanline_dark)),
            Rect::new(area.x, y, area.width, 1),
        );
    }
}
```

Scanline intensity varies with agent phase:
- Idle / no runs: intensity 0.12
- Active run: intensity 0.14
- Multiple active runs: intensity 0.20
- Approval pending: intensity 0.30 (heightened urgency)

#### B.3.3 Noise Floor

Sparse random cells are rendered with rose-ember or noise-cool characters
(`·`, `∙`, `·`) at a density of 0.003–0.020 of total cells. Driven by
`InterpolatingChannels.noise_floor` (rate 0.15 — slow response).

```rust
fn apply_noise(frame: &mut Frame, area: Rect, density: f64, theme: &Theme) {
    use rand::Rng;
    let mut rng = rand::thread_rng();
    for y in area.y..area.y + area.height {
        for x in area.x..area.x + area.width {
            if rng.gen::<f64>() < density {
                // Paint a noise character only if the cell is empty (bg only)
                // Uses ROSE_DEEP for warm noise, NOISE_COOL for cool noise
                let color = if rng.gen::<bool>() {
                    theme.noise_warm
                } else {
                    theme.noise_cool
                };
                frame.render_widget(
                    Paragraph::new("·").style(Style::default().fg(color)),
                    Rect::new(x, y, 1, 1),
                );
            }
        }
    }
}
```

#### B.3.4 Breathing Animation

Active agent panels exhibit a subtle border glow animation, lerping the border
color between `border` and `border_active` on a 2–4 second cycle. The cycle
length is derived from `DesignTokens::FREQ_F3` (incommensurate with F1/F2 to
avoid visual periodicity).

```rust
fn breathing_border_color(t: f64, theme: &Theme) -> Color {
    // t in [0, 1), one breath cycle
    let phase = (t * std::f64::consts::TAU).sin() * 0.5 + 0.5;
    lerp_color(theme.border, theme.border_active, phase as f32 * 0.4)
}
```

The `0.4` clamp prevents the breathing from reaching full `border_active`
(which would look identical to a focused border), keeping the animation subtle.

| Circuit broken | 0.20 | 0.008 | Pulse (amber) |
| Error / failed | 0.30 | 0.015 | Static (crimson) |
| Stopped | 0.14 | 0.004 | None |

## APPENDIX E: REAL-TIME STREAMING ARCHITECTURE

### E.1 WebSocket Agent Output Streaming

Polkagent uses the same `AgentStreamClient` pattern as Roko, adapted for the
`polkagent-serve` WebSocket event bus. The client runs on a Tokio background
task; the TUI polls it non-blocking on each frame tick.

```rust
// polkagent-cli/src/tui/ws_client.rs
// Direct port of Roko's crates/roko-cli/src/tui/ws_client.rs

use tokio::sync::mpsc::{Receiver, Sender};
use tokio::task::JoinHandle;

const CHANNEL_CAPACITY: usize = 256;
const INITIAL_BACKOFF_SECS: u64 = 1;
const MAX_BACKOFF_SECS: u64 = 30;

/// One chunk emitted to the TUI render loop.
#[derive(Debug, Clone, PartialEq)]
pub enum StreamChunk {
    Connected,
    Text(String),
    Reasoning(String),        // extended thinking
    ToolCall(serde_json::Value),
    EffectProposal(serde_json::Value), // agent proposing an on-chain effect
    Usage { tokens: u64, cost_usd: f64 },
    Error(String),
    Done { session: Option<String> },
    Disconnected,
}

/// Background WebSocket consumer for one agent's live output stream.
pub struct AgentStreamClient {
    rx: Receiver<StreamChunk>,
    task: JoinHandle<()>,
}

impl AgentStreamClient {
    /// Connect to polkagent-serve event bus, filtering for one agent_id.
    pub fn connect(
        agent_id: impl Into<String>,
        serve_base_url: &str,
        auth_token: Option<String>,
    ) -> Option<Self> {
        let handle = tokio::runtime::Handle::try_current().ok()?;
        let agent_id = agent_id.into();
        let endpoint = ws_endpoint(serve_base_url);
        let (tx, rx) = tokio::sync::mpsc::channel(CHANNEL_CAPACITY);
        let task = handle.spawn(run_agent_stream(agent_id, endpoint, auth_token, tx));
        Some(Self { rx, task })
    }

    /// Non-blocking poll — called once per frame tick.
    pub fn try_recv(&mut self) -> Result<StreamChunk, tokio::sync::mpsc::error::TryRecvError> {
        self.rx.try_recv()
    }
}

impl Drop for AgentStreamClient {
    fn drop(&mut self) {
        self.task.abort();
    }
}
```

**Connection lifecycle:**
1. `AgentStreamClient::connect()` spawns a background Tokio task.
2. The task connects to `wss://serve.polkagent.io/ws` with a Bearer token.
3. On connect, it sends a subscribe message: `{"subscribe": ["agent_output"], "agent_id": "..."}`.
4. It pumps incoming frames through `parse_frame()` and emits `StreamChunk`s.
5. On disconnect, it emits `StreamChunk::Disconnected` and retries with
   exponential backoff (1s → 2s → 4s → ... → 30s max).
6. The TUI's `drain_agent_stream_chunks()` calls `try_recv()` in the render
   loop's channel drain phase, consuming chunks without blocking.

**Source:** Roko `crates/roko-cli/src/tui/ws_client.rs` — complete production
implementation with event bus subscription and sidecar frame parsing.

### E.2 Interpolating Channels for Smooth Animation

Polkagent uses the 32-channel interpolating variable system from Bardo's
`apps/bardo-terminal/src/channels.rs`. All visual metrics converge smoothly
using exponential decay rather than snapping.

```rust
// polkagent-cli/src/tui/channels.rs
// Adapted from Bardo apps/bardo-terminal/src/channels.rs

/// Exponential decay channel: current converges toward target each frame.
#[derive(Debug, Clone, Copy)]
pub struct Channel {
    pub current: f32,
    pub target: f32,
    pub rate: f32,   // higher = faster convergence
}

impl Channel {
    pub fn new(initial: f32, rate: f32) -> Self {
        Self { current: initial, target: initial, rate }
    }

    pub fn tick(&mut self, dt: f32) {
        let alpha = 1.0 - (-self.rate * dt).exp();
        self.current += (self.target - self.current) * alpha;
    }

    pub fn set_target(&mut self, target: f32) {
        self.target = target;
    }
}

/// Polkagent interpolating channels (subset of Bardo's 32-channel system).
pub struct PolkagentChannels {
    // Fast (rate 8–15): UI elements that respond quickly
    pub approval_urgency: Channel,  // 0.0–1.0: drives approval panel highlight
    pub agent_activity:   Channel,  // 0.0–1.0: breathing animation intensity
    pub inference_glow:   Channel,  // 0.0–1.0: brightness during LLM call

    // Medium (rate 1–2): slower-responding visual elements
    pub context_utilization: Channel, // 0.0–1.0: context gauge fill
    pub budget_utilization:  Channel, // 0.0–1.0: budget gauge fill
    pub run_count_norm:      Channel, // normalized active run count

    // Slow (rate 0.1–0.3): atmosphere and global state
    pub scanline_intensity: Channel, // 0.0–0.5: scanline density
    pub noise_floor:        Channel, // 0.0–0.02: noise cell density
    pub health_composite:   Channel, // 0.0–1.0: overall system health

    // Free-running
    pub breath_phase: f32, // advances by dt * TAU each frame
}

impl PolkagentChannels {
    pub fn new() -> Self {
        Self {
            approval_urgency:   Channel::new(0.0, 12.0),
            agent_activity:     Channel::new(0.0, 8.0),
            inference_glow:     Channel::new(0.0, 10.0),
            context_utilization: Channel::new(0.0, 2.0),
            budget_utilization:  Channel::new(0.0, 1.5),
            run_count_norm:      Channel::new(0.0, 1.0),
            scanline_intensity:  Channel::new(0.12, 0.15),
            noise_floor:         Channel::new(0.003, 0.15),
            health_composite:    Channel::new(1.0, 0.2),
            breath_phase:        0.0,
        }
    }

    pub fn tick(&mut self, dt: f32) {
        self.approval_urgency.tick(dt);
        self.agent_activity.tick(dt);
        self.inference_glow.tick(dt);
        self.context_utilization.tick(dt);
        self.budget_utilization.tick(dt);
        self.run_count_norm.tick(dt);
        self.scanline_intensity.tick(dt);
        self.noise_floor.tick(dt);
        self.health_composite.tick(dt);
        self.breath_phase += dt * std::f32::consts::TAU;
    }
}
```

### E.3 Filesystem Watcher

The `.polkagent/` directory is watched for changes using `notify` (cross-platform
fs events). On any change, a debounced refresh event is sent to the TUI's
channel, triggering a state reload without polling.

```rust
// polkagent-cli/src/tui/fs_watch.rs
// Direct analog of Roko's crates/roko-cli/src/tui/fs_watch.rs

use notify::{RecommendedWatcher, RecursiveMode, Watcher, event::EventKind};
use std::sync::mpsc;
use std::path::PathBuf;
use std::time::{Duration, Instant};

const DEBOUNCE_MS: u64 = 100;

pub struct FsWatchHandle {
    _watcher: RecommendedWatcher,
    pub rx: mpsc::Receiver<FsRefreshEvent>,
}

#[derive(Debug, Clone)]
pub enum FsRefreshEvent {
    AgentsChanged,
    RunsChanged,
    ConfigChanged,
    LogsChanged,
}

impl FsWatchHandle {
    pub fn start(polkagent_dir: PathBuf) -> anyhow::Result<Self> {
        let (tx, rx) = mpsc::channel();
        let mut watcher = notify::recommended_watcher(move |event: notify::Result<notify::Event>| {
            if let Ok(event) = event {
                // Route events to the appropriate refresh type
                let kind = match event.kind {
                    EventKind::Create(_) | EventKind::Modify(_) | EventKind::Remove(_) => {
                        classify_event(&event.paths)
                    }
                    _ => return,
                };
                if let Some(kind) = kind {
                    let _ = tx.send(kind);
                }
            }
        })?;
        watcher.watch(&polkagent_dir, RecursiveMode::Recursive)?;
        Ok(Self { _watcher: watcher, rx })
    }

    /// Non-blocking poll — called once per frame in channel drain phase.
    pub fn try_recv(&self) -> Option<FsRefreshEvent> {
        self.rx.try_recv().ok()
    }
}
```

**Source analog:** Roko `crates/roko-cli/src/tui/fs_watch.rs` (fs event
watcher with debouncing), Roko `crates/roko-cli/src/tui/jsonl_tailer.rs`
(JSONL file tailing for episode log).

### E.4 Chain Block Subscription

The chain subscription runs as a Tokio background task, subscribing to finalized

```rust
pub fn start_chain_subscription(
    profile: ChainProfile,
    tx: tokio::sync::watch::Sender<ChainHeadSnapshot>,
) -> tokio::task::JoinHandle<()> {
    tokio::spawn(async move {
        let mut backoff = 1u64;
        loop {
            match connect_and_subscribe(&profile, &tx).await {
                Ok(()) => { backoff = 1; }
                Err(e) => {
                    tracing::warn!("Chain subscription error: {e}. Retrying in {backoff}s.");
                    tokio::time::sleep(Duration::from_secs(backoff)).await;
                    backoff = (backoff * 2).min(60);
                }
            }
        }
    })
}
```

The TUI polls the `watch::Receiver` in `drain_chain_subscription()` and updates
`TuiState.chain_heads` on change. This drives the ChainStatus widget and the
block number in the HeaderBar.

### E.5 Approval IPC

Approval requests arrive from the kernel (running in-process or via Unix socket)
through a `mpsc::Receiver<ApprovalRequest>`. The TUI drains this channel and
opens an `ApprovalModal` when a request arrives.

```rust
#[derive(Debug, Clone)]
pub struct ApprovalRequest {
    pub approval_id: String,
    pub agent_id: String,
    pub run_id: String,
    pub action_card: ActionCard,   // typed, canonical data
    pub deadline: DateTime<Utc>,
    pub response_tx: Arc<Mutex<Option<oneshot::Sender<ApprovalResponse>>>>,
}

#[derive(Debug, Clone)]
pub enum ApprovalResponse {
    Approved { payload_hash: String },
    Denied { reason: Option<String> },
}
```

When the user presses `y` (approve) or `n` (deny) in the `ApprovalModal`, the
TUI sends the response through the `oneshot::Sender`, which resolves the
kernel's pending approval future. This is the same pattern Roko uses for
`pending_approval_response: Option<oneshot::Sender<bool>>` in its `App` struct.

### E.6 Backpressure Handling

If the agent output stream produces chunks faster than the TUI can drain them,
the `CHANNEL_CAPACITY` of 256 items acts as a backpressure buffer. When the
buffer is full, `try_send()` returns `TrySendError::Full` and the background
task pauses briefly (yield_now). This prevents the TUI from falling behind on
fast-streaming agents while keeping memory bounded.

For chain subscriptions, the `watch::Sender` pattern naturally provides
backpressure: only the latest value is retained; intermediate values are
discarded if the receiver cannot keep up. This is appropriate for block headers
(only the latest matters) but not for agent output (every token matters). Hence
the different channel types.


### G.4 Machine-Parseable Exit Codes

```
0   Success
1   General error (see stderr for details)
2   Approval required (non-interactive mode, no --yes)
3   Policy denied
4   Configuration error
5   Network / chain error (RPC unreachable, stale metadata)
10  Unknown outcome (effect submitted, finality not confirmed)
```

Exit code 10 is especially important: it means the command completed but the
outcome is unknown. Scripts must treat code 10 as "check manually" rather
than "failed".

### G.5 --no-color and --plain-text Modes

`--no-color` suppresses all ANSI escape codes. Activated automatically when:
- `NO_COLOR` environment variable is set (any value)
- The output is not a TTY (`isatty()` returns false)
- `--no-color` flag is explicitly passed

`--plain-text` additionally removes all Unicode symbols (◉ → *, ✓ → ok, etc.),
for maximum compatibility with screen readers and minimal-capability terminals.
